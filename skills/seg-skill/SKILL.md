# 目标分割任务算法

把业务需求转成可计算、可配置、可测试的开发规范。按“业务 → 标签 → ROI/mask → 几何量 → 过滤 → 时序 → 输出 → 验收”形成闭环。默认交付中文 Markdown。

## 1. 读取并确定依据

1. 读取用户当前附件与实际方法论，不能仅依据文件名、记忆或搜索摘要。
2. 用户给出本地附件路径时直接读取；DOCX 提取正文、表格，示例图涉及标签边界时查看图片。不能把检测框假定为分割轮廓。
3. 新任务优先读取 `references/methodology.md`；若当前提供更新的方法论，以新文件为准。该参考含历史“必须增加面积上限/帧投票”等要求时，只作为设计候选，不覆盖当前明确删减。
4. 采用优先级：当前明确指令 → 用户指定的人工最终版 → 当前标注方案与既定接口 → 已确认历史修改 → 方法论 → 设计建议。若高优先级来源自身矛盾，列出矛盾，不悄悄替用户裁决。
5. 对比人工版与上一交付版时，先做文本 diff 与文件哈希，再做业务语义核对。
6. 交付中文 Markdown中不需要出现信息来源备注（例如，配置按《# EV_SDK配置协议.md》第 2、3、5 节实现），不需要出现版本差异、日期、依据信息

## 2. 建立需求基线

在工作过程中维护下表，不必向用户输出全部中间表：

| 需求项 | 来源/原句 | 已确认或建议 | 参数/公式 | 输出字段 | 验收案例 |
|---|---|---|---|---|---|

至少覆盖业务目标、任务类型、模型与精度/速度偏好、标签及标注方式、ROI 容器与元素含义、计算公式、过滤、时序、参数类型、交付格式。每个参数和输出字段都要能追溯到实际用途或明确接口要求；另维护删除参数清单，防止后续模板重新引入。

把信息分成：明确要求、附件事实、必要工程定义、可选建议、待确认项。对可逆细节给出标注为建议的默认值；仅对会改变业务语义且无法合理确定的问题询问。不要给每个可能的优化增加一个开关。

## 3. 选择可执行规则

阅读 `references/rules.md`，按本次任务选择，不套用全部策略。

- 选择区域占比、连通域关系、状态变化或检测分割融合类型。
- 空间关系先按业务问题选度量，再设阈值。大小差异明显、随距离改变像素面积的对象，判断小目标落入大目标的程度时优先用交集面积 / 小目标有效面积；不能直接套用 IoU 或绝对交集像素阈值。
- 每个比例写清分子、分母、坐标尺度、逐实例/合并规则、零分母处理和阈值方向；给可复算的算术示例，并检查小于、等于、大于阈值三种情况。具体案例的 0.95 不能变成所有任务的默认值。
- 公式首次出现时就解释每个符号的业务含义、类型、取值和作用范围，区分可配置参数与运行时计算量。单帧票必须说明在统计什么、为什么需要、何时记 1/0/未知，以及如何进入最终报警。
- 明确每个标签是报警、状态、辅助或过滤标签；半开状态可能同时有开口和门体，不能按标签名称推断互斥。
- 固定 ROI 对象优先按视频流 + ROI 索引维护独立状态；移动目标需要另定义关联，不能复用模型每帧实例下标。
- 分开写单帧候选与最终报警。区分连续时长、时间投票、帧投票，不通过改参数名偷偷更换时序语义。分别投票后组合与同帧条件取交集后投票不等价；不得未经需求依据把前者改成后者。
- 明确正常、异常、未知；规定未知帧、漏检、遮挡、断流、倒退时间戳、重启与配置变更如何影响历史。
- 报警输出与重复通知分开定义，说明事件开始、维持、结束、重触发。

## 4. 生成文档

使用 `assets/document-template.md`，按任务删去不适用占位项。需要沿用本项目接口时再读取 `references/accepted-case.md` 和 `references/unloading-platform-final.md`；不要默认加载完整案例。

遵守本项目已确认的写作偏好：

- 参数与功能同步，表中给名称、类型、默认值、单位、范围、生效条件。
- 参数和输出字段先做用途检查：说明谁使用、在哪条规则或哪项接口中使用、去掉后影响什么。模板中出现过不构成保留理由；没有用途的可选字段删除，既定接口必填字段保留并解释作用。`area_ratio` 只在实际参与判断或明确输出需求时保留，内部计算量不自动成为输出字段。
- 参数直接在业务分区回显，不再包一层 `config`。
- 默认复用已接受的“标量/数组参数 + 定长数组记录”接口；协议的 `algorithm_data`、`model_data` 对象容器与字典类型参数不是一回事。新任务指定不同接口时以新接口为准。
- 定长数组必须列字段顺序、索引、类型、空值占位、长度与关联方式。用户若要求连协议容器也不能使用对象，则改用完整数组协议并重新定义位置，不能声称对象不存在。
- `target_info` 只放当前报警对象，数量等于 `target_count`；模型数据可包含未报警及辅助目标。
- 提供报警、不报警、过滤/未知三类示例；多 ROI、时序或边界复杂时增加相应用例。
- 对没有实测依据的精度、最小像素尺寸、硬件速度写“待验证”；合成算例不能称为实测。
- 先写开发执行所需内容，避免把泛泛行业背景塞入交付文档。
- 不需要过度思考（例如，激活锁，区域锁相关点的策略与逻辑（不用考虑异常情况），验收用例与迭代边界，结论与开发约束）

## 5. 处理修改

把每条修改传播到：正文、流程/公式、状态机、参数表、示例、字段解释、可视化、验收用例、结论。

- 删除参数时同时处理功能、依赖、旧默认值及输出字段，不只删表格行；删除调参入口与删除算法必要标准后处理应区别处理。
- 改默认值时检查等于阈值是否触发，修改对应数字例子，不替换恰好相同但含义不同的观测值。
- 人工最终版中的工程建议不自动变成实测结论。用户指定其为开发基线，可作为该案例认可口径；不能把专用阈值提升为全部分割任务通用标准。
- 不修改用户的最终版原件，除非用户要求修改。

## 6. 验证并交付

运行 `scripts/check_document.py FILE --forbid <被删除参数> ...` 检查 JSON 语法、字典参数、数量一致性与删除项残留。运行 `--compare ORIGINAL FINAL` 可得到哈希与差异统计。脚本只检查结构，不能替代以下人工语义检查：

1. 每条明确需求都有公式/规则与验收案例对应。
2. 几何度量符合业务关系；比例分母、逐实例/并集规则、坐标与面积一致；mask 来源与标注类型一致。
3. AND/OR、阈值等号、时序初始化/重置/恢复无歧义，多目标隔离。
4. 所有参数在正文、表、JSON 中一致，删除项无残留；数组索引前后一致。
5. 算例的面积、比例、时长与报警状态能手工复算。
6. 每个参数和输出字段有实际用途或明确接口要求；公式符号定义齐全，单帧票、窗口比例和最终报警可逐步复算；未擅自增加同帧门控或把未知当作正常/异常。
7. 所有参数设计符合 `references/EV_SDK配置协议 .md` 中的约定；按当前明确需求处理协议适用范围。

评分使用 `references/rules.md` 的评分表，低于 90 分或命中硬性缺口先修订。没有现场测试只能报告文档检查通过，不能报告算法效果通过。

按用户要求创建/更新交付文件，并按当前环境的文件持久化规范保存；已有文件修改保留身份与版本。最终简述完成项、重要差异、仍需确认的业务变量，提供最终文档链接。后续人工反馈回到需求基线，形成下一版。
